# 公开发布前检查

这是维护者公开自己副本时的流程，不代表仓库已经 public，不记录作者的部署信息。

## 内容和交接

- [ ] 所有公开引用和历史均不含真实地址、私有域名、凭证、会话、数据库、音频和备份。
- [ ] 本地内容检查与通用凭据扫描通过，提交消息、示例、fixture 已审查。
- [ ] GitHub 分支、标签、PR、issue、评论、Actions 日志及产物、Release、Wiki、附件已审查。
- [ ] LICENSE 已确定，第三方代码与资源遵守原许可。
- [ ] 独立 clone 可按文档完成安装、配置和测试。
- [ ] 自己的实例完成浏览器、TTS、扩展和 Podcast 验收。

## 从私有历史转为公开

旧历史包含不希望公开的信息时，有两条路径：

1. 旧仓库保留 private，创建没有 fork 关联的全新公开仓库，只上传审核过的干净源码或清理后的历史。旧仓库对象不会因可见性变更一起公开。
2. 用 git-filter-repo 在独立克隆重写所有相关引用，复核后受控强推，并清理旧克隆。强推成功不代表 GitHub 缓存和其他引用已消失。

不要从含私有历史的目录直接 `git push --mirror` 到 public。原始 Git bundle 和维护资料只保存在本地私有备份。

发布前记录远端引用、备份、替换范围和候选提交。强推使用明确引用与 `--force-with-lease`，防止覆盖准备期间的新提交。旧克隆重新克隆或迁移，不能 merge 旧历史回来。

详见 [GitHub 敏感数据清理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

## 交给新的维护者

交付仓库链接、README、AGENTS.md、上手指南、配置表、检查命令和已知限制即可。新维护者建立自己的实例。父子之间若共享现有实例，通过单独私有渠道管理，不把访问资料补进公共文档。

## 后续可以独立开发的方向

- 移动端播放、离线缓存的实机回归。
- 快照保留期限、删除策略、扩展凭证改用本地存储。
- 自动备份及恢复演练、磁盘限额、依赖升级检查。
- 登录限速、URL 内网访问限制、面向不可信用户的权限设计。
- 全文搜索、其他语音引擎；多用户和多 worker 先设计数据隔离及队列。

这些是候选方向，不是已经实现的功能，不要求第一次接手一次完成。
